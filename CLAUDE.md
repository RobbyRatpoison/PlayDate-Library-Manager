# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

PlayDate is a local game library manager. It runs as a Flask web server wrapped in a native OS window via pywebview (no Electron). Users browse their Steam and GOG libraries, apply filters, track completion, and use a "Pick 6" feature to discover what to play next. Non-Steam games use negative integer appids. Non-Steam library sources (GOG, Epic, etc.) are optional plugins. None of them ship as source in this repo, including PlayDate's own first-party ones (GOG, EA App, Epic Games, Humble Bundle, IndieGala, itch.io, Ubisoft Connect, Battle.net, Rockstar Games, Amazon Games, Legacy Games, Xbox / Game Pass) — they're published as their own GitHub repos and installed like any third-party plugin (see Plugin System below), not bundled with the app. Plugins fall into two broadly standardized shapes — launcher-based and no-launcher — with no single "gold standard" implementation for either.

## Running & Building

```bash
python main.py              # development (Flask + pywebview window)
python app.py               # Flask only, browser at localhost:5000
pyinstaller playdate.spec   # Windows exe; then Inno Setup 6 for installer
python install.py           # Linux/macOS GUI installer
./launch.sh                 # Linux/macOS: runs install.py on first run, then launches
```

**macOS launch (v1.11.1, confirmed on a real Mac):** `PlayDate.command` (double-clickable, opens Terminal) just `exec`s `launch.sh`. On Darwin, `launch.sh` picks the Python for `install.py` via `find_mac_python()`, not the system `python3`: it needs 3.10+ (`PLAYDATE_MIN_PY_MINOR`, matching `install.py`) with tkinter/venv/ensurepip, searched in the python.org framework, Homebrew and PATH. It skips Apple's `/usr/bin/python3` stub unless `xcode-select -p` succeeds (running the stub on a fresh Mac triggers the multi-GB Command Line Tools download). If nothing qualifies, `mac_python_missing()` offers a Homebrew install (`python@3.12` + `python-tk@3.12`), else opens python.org and waits for Enter; from `PlayDate.app` (no terminal) it shows an `osascript` dialog and exits. Linux keeps plain `python3` (must match the distro's `python3-gi`). Keep `PLAYDATE_MIN_PY_MINOR` in sync with `requirements.txt`/`install.py`.

**Icons:** `static/img/favicon.png` (512px, padding-free) is the single source for the window/Linux/Flatpak icons, splash, the userscript's `@icon`, and CI's Windows `favicon.ico` and Flatpak hicolor sizes. The macOS bundle icon is `static/img/favicon.icns` (macOS needs `.icns`), generated with Pillow from the 1024px logo art (colours matched to the previous logo: saturation x1.38, brightness x0.965; cropped, centred on a square canvas at ~824 of 1024px for Apple's ~100px margins), copied into `Contents/Resources` by `launch.sh` and `install.py`'s `_register_macos()`. Replacing the logo means replacing the PNG and regenerating the `.icns`.

**Tests:** `pytest tests/` (deps in `requirements-dev.txt`; CI: `.github/workflows/tests.yml` on push/PR to main/dev). It covers pure logic: filter tree -> SQL (`build_tree_sql`, `is_safe_sql`), `classify_category`, `parse_appinfo` (synthetic file), `parse_playnite_fields` (synthetic LiteDB-shaped files), review weighting, `review_score_label`, the PAGYWOSG event-id formula, `scrapers.clean_description` / `description_lookup_due`, `images.art_source_order`, and duplicate links (`test_duplicate_links.py`, the one DB test: it monkeypatches `database.get_db` to a throwaway sqlite file). `test_name_sort_case.py` fails on any root-module `ORDER BY name` without `COLLATE NOCASE` (see Sorting Names). Routes and UI are not exercised: verify by running the app (Playwright + Chromium is in `.venv`; use an isolated copy of the project, never the real data dir). Run the suite when touching these functions; add a test case for each new `classify_category` branch or `OP_REGISTRY` op.

**Lint:** `ruff check .` (`ruff.toml`, pyflakes rules only; no style rules, since the dense one-liner style doesn't fit pycodestyle). Runs in CI. A few pre-existing bugs it caught that aren't safe to fix blindly are marked `# noqa: F821` with a comment (e.g. `plugins/gog/gog.py`'s `_fetch_all_products`/`p`, silently swallowed by an `except Exception`).

## Architecture

Flask + pywebview hybrid. Waitress WSGI (8 threads). `main.py` starts Flask in a background thread, opens the pywebview window, then starts filesystem watcher and playtime sync threads.

**Port selection (v1.11.1):** PlayDate serves on `PORT` (5000), falling back to `FALLBACK_PORT` (2468) when 5000 is held by something that isn't PlayDate — chiefly macOS's AirPlay Receiver, which listens on 5000 (and 7000) by default (not yet confirmed on a real Mac). `main.py`'s `_choose_port()` decides: a connect (`_port_listening()`, never a bind — a bind check false-positives on TIME_WAIT and behaves differently per OS next to a wildcard listener) then `_is_playdate()`, which recognises PlayDate by waitress's `Server` header on a 404 from `/__ready__` (AirPlay answers `AirTunes`; also matches older PlayDate versions). A live PlayDate on either port returns `'running'` and the second launch shows the "already running" window and exits — **this guard must stay**, otherwise a second launch would fall back to 2468 and run a second instance against the same database. `PORT`/`URL` are reassigned at startup, so anything that needs the port must read the module globals, never a hard-coded 5000. `steam_date_import.user.js` probes both ports (`PD_PORTS`, via `/api/update-status`); keep its list in sync with `main.py`, and bump its `@version` when it changes since an installed copy keeps talking to 5000 only until updated.

**Routes live as Flask Blueprints, one per domain module** — each `_bp` is a module-level `Blueprint(...)` defined and registered directly in that domain's own file (not nested in a factory function), following the pattern `config_bp`/`index_bp`/`library_bp` established first. `app.py` itself only holds the app factory (`create_app()`), blueprint registration, static file serving, the CORS/context-processor hooks, and the populate/scrape-new-games routes (kept here because `main.py` imports the shared `populate_cancel` event directly from `app`). When adding a new route, add it to the blueprint whose file already owns that domain's logic; only create a new blueprint module for a genuinely new domain.

## Database Schema Notes

- `completion_status`: `'Never Played'`, `'Unfinished'`, `'Beaten'`, `'Completed'`, `"Won't Play"`. `"Won't Play"` means the user has decided not to play the game, **for any reason they choose** — broken, bad, or simply not interesting (the owner confirmed this for v1.11.2; user-facing copy must not narrow it). So don't build an algorithm on it as a strong dislike signal; today nothing does (tag similarity's negative pool is the whole library, see Key Patterns → Cached Derived Stats, and Pick 6 only uses it as a status filter). `'Completed'` means 100% achievements; `'Beaten'` is a subjective per-game call otherwise.
- Comma-separated columns (`tags`, `groups`, `developers`, `publishers`): no spaces after commas
- Dates as Unix timestamps (INTEGER): `date_added`, `last_played`, `release_date`
- `platform`: `'steam'`, `'gog'`, `'epic_games'`, `'ea_app'`, `'ubisoft'`, plus every plugin's platform and `'custom'` (games added by hand with no store behind them, see Add Game; displayed as "Manual" in the UI as of v1.11.3 -- the stored value and internal references are still `'custom'`, only `_CORE_PLATFORM_LABELS`' display string changed)
- `duplicate_of`: TEXT appid of the copy that is *shown*; `NOT NULL` = this copy is hidden (excluded from the library by default). `duplicate_auto` = 1 for a name match found by detection, 0 for a link made by hand. See Duplicate detection under Plugin System: the platform priority order always decides the direction.
- `metacritic_score` (INT, NULL = none): Metacritic score from the Steam store API (`fetch_store_data`), shown as "Critic %". Only ~40% of Steam games have one.
- `short_description` (TEXT): plain-text store blurb, stored by populate/rescrape or lazily by `/api/game-description`; `short_description_checked` (YYYY-MM-DD) = a lookup found nothing, don't ask again for 14 days (see Stored Descriptions)
- **GOG appids are negative integers.** Flask uses `SignedIntConverter` (`r'-?\d+'`) for routes; `appid_list` validation allows zero/negative.
- `blacklist` table prevents repopulation of removed games
- `tag_similarity`: cached derived stat, see Key Patterns → Cached Derived Stats
- **Non-Steam platform columns:** `platform_id` = service-native catalog/item ID (e.g. Epic `catalogItemId`, GOG product ID); `platform_slug` = store URL slug (e.g. `epicgames.com/p/{slug}`); `platform_appname` = internal launch/install name where it differs from the slug (Epic only — `appName` used in protocol URLs and install dirs); `platform_ns` = catalog namespace (Epic only). For Epic, `platform_id` and `platform_appname` are both needed: `platform_id` is used for catalog API calls and dedup; `platform_appname` is used for launching and install detection. Epic's assets API can return multiple records with the same `catalogItemId` but different `appName`s (entitlement vs installable); the sync resolves the correct one via `releaseInfo[*].appId` where `platform` includes `'Windows'`.

## PyInstaller Path Handling (Critical)

- **Bundle assets** (templates, static): `sys._MEIPASS` when frozen
- **User data**: `os.path.dirname(sys.executable)` when frozen, `__file__` dir otherwise

User data lives *next to* the .exe so it survives upgrades. Never use bare `__file__` for runtime paths — always use `BASE_DIR`.

## Filter System

Recursive JSON tree compiled to SQL by `library.build_tree_sql()`.

- **Node types**: `'condition'`, `'group'` (AND/OR), `'custom_expr'` (raw SQL)
- **Comma-separated fields** (tags, groups, genres, categories): use `',' || column || ',' LIKE ?` to prevent partial matches
- **Date operators**: `STRFTIME_MONTH/DAY/YEAR` compile to `strftime(...)` with zero-padded values
- **SQL safety:** `is_safe_sql()` in `library.py` uses column/keyword/function whitelists, rejects all DML/DDL. Parameterized queries everywhere else.
- **Cover Shape filter (`cover_fit`, 2026.10.4):** a regular condition field (`FM_FILTER_CONFIG` in `modal_filters.html`), not a preset and not a real column: `library._cover_fit_sql` turns `= / != fits|wrong|none` into SQL over `edge_horizontal` when the saved `artwork_orientation` is `horizontal`, else `edge_vertical` (list view counts as vertical), because a game can fit in one view and not the other (see Card Edge Backdrops for what the column holds). Because the SQL differs per view it is part of the Library data key, so switching view gives a fresh list. Home and Pick 6 compile it with the same saved view, though Home only shows vertical covers. It is not in `SAFE_COLUMNS`, so custom SQL can't use it. `tests/test_cover_fit_filter.py`.
- **PAGYWOSG filters** save as full tree structures (not raw SQL) so they're editable. `populateModalFromTree` explicitly clears the custom SQL box when no `custom_sql` key is present, to prevent stale SQL bleed.
- **Preserving PAGYWOSG keys:** `applyFilters()` copies `pagywosg`, `pagywosg_event`, `pagywosg_verified` from `_loadedSavedTree` onto the rebuilt tree.

## Key Patterns

### Threading & Cancellation
Long-running operations run in daemon threads with `threading.Event` (`_populate_cancel`). Progress tracked in `_populate_state`, polled via `/api/populate-status` every second.

### Scrapers

**Rate limiting:** fetch functions raise `RateLimitedError` on 429 with `retry_after` (seconds, from `Retry-After` via `_parse_retry_after()`) when present. Populate and bulk-rescrape workers share a `_PoolBackoff` gate per pool (meta/cheevo/bulk_rescrape): the first 429 closes the gate and all workers wait together, preferring `retry_after` over the fixed `BACKOFF_DELAYS` (`[15, 60, 300, 3615]`), capped at the largest delay; once all are exhausted the pool aborts. `sync_store_release_dates`/`sync_store_names` (startup migrations) pause and retry once, also preferring `retry_after`. `/api/scrape_single/<appid>` catches `RateLimitedError` and returns a `429` with a clear message.

**API key optional:** without one, `add_new()` reads local Steam files (`localconfig.vdf` playtime, ACF names, `appinfo.vdf` names/types). Achievements are skipped; Store API, reviews and tag scraping still work.

**`parse_appinfo()`** (`utils.py`) parses Steam's binary `appinfo.vdf` (v29, magic `0x07564429`) with custom struct code; the `vdf` package only reads text VDF.

**Startup playtime sync:** reads `localconfig.vdf`, updates playtime + last_played; for changed playtime re-fetches achievements; `'Never Played'` -> `'Unfinished'` if playtime > 0 (`auto_promote_unfinished`). `scrapers._sweep_achievement_completion_status()` then corrects `completion_status` from stored achievement counts, Steam-only, gated by two settings (Library modal, Completion Sync): `auto_complete_on_100pct` (any status -> `'Completed'` at 100%, default on) and `auto_downgrade_completed` (`'Completed'` -> `'Beaten'` when counts no longer show 100%, default on). Also called after `bulk_rescrape_games()`.

**BLAEO sync:** plain `requests` + `BeautifulSoup`, no browser automation; `data-value='-2'` on the achievements cell = no Steam achievements, skip.

**Review confidence weighting:** `utils.weighted_review_score(percent, count, half_trust=10)` = `round((p - (p - 0.5) * 2^(-ln(count + 1)/ln(half_trust))) * 100)`, pulling low-count scores toward 50. `half_trust` (state `review_half_trust_count`, default 10, reproducing the original `2^(-log10(total + 1))`) is the `count + 1` at which a score is trusted halfway. `scrapers._weighted_score()` reads it at scrape time; `database.recalculate_weighted_scores()` rewrites `weighted_percentage` from raw `review_percentage`/`total_reviews` when it changes. **Steam rows only**: plugins that report reviews (Epic Games) use their own formula, which a recompute must not overwrite (it once silently changed 100 Epic rows). It also filters on `typeof(...)` since legacy rows can hold `''` and `'' > 0` is true in SQLite.

**Tuning modal (Settings -> Tuning, `tuning-modal`)** is the one home for arbitrary-constant formulas: tag similarity (`tag_similarity_*`), review half-trust, `pick6_*` caps/blend. `modal_tools.js`'s `TUNE_SECTIONS` declares sections/sliders and `TUNE_CHARTS` the per-slider graphs (solid = slider, dashed = saved). **`TUNE_CHARTS` re-implements the real formulas client-side: update it when `database.py`/`pick.py`/`utils.py` change.** A section's `recalc` URL is POSTed after saving. To add a tunable: state default + `save_state` validator in `config.py`, add to `window._TUNE_INIT` in `modal_tools.html`, then a `TUNE_SECTIONS` entry. The six Pick 6 signal weights stay on the Pick 6 page.

### Cover Art Pipeline
Three types: vertical capsule, horizontal header, icon. The Steam asset manifest is fetched once per game and shared. Non-Steam: `_sgdb_search_game_id(name)` -> SGDB game ID -> direct query. All JPEG 95 (RGBA/WEBP -> RGB), cached locally, not re-fetched unless deleted.

The original ("auto") chain, still used for an uncustomised library and every Steam game unless its order is edited: **Vertical** manifest -> CDN `library_600x900` -> SGDB grid; **Horizontal** manifest -> CDN `header.jpg` -> SGDB wide; **Icon** SGDB icon -> Steam hash.

**Artwork Sources (v1.11.2): ordered sources per library and art type.** `state.json` `art_source_prefs` = `{platform: {vertical|horizontal|icon: ['store','sgdb','steam', ...]}}`, `[]` meaning "fetch nothing". `download_vertical/horizontal/icon` call `_download_art`, which resolves the order via the pure `art_source_order(kind, platform, has_store, saved, default)` and tries sources until one returns something other than `'missing'`. The old bodies are `_download_vertical/_horizontal/_icon`, the `'steam'`/`'sgdb'` runners, now **strict** (`'sgdb'` never falls to a Steam-by-name lookup and vice versa) so a switched-off source never leaks in. An explicit `source=` (the edit modal's picker) bypasses the order. Saved lists are honoured exactly; `config.save_state` validates them (unknown names/duplicates dropped, `[]` kept).
- **The automatic SteamGridDB scrape uses the picker's ordering (2026.10.4):** `_sgdb_download_best` (used by `_download_vertical/_horizontal/_icon`) takes `_sgdb_options_from`'s order (closest to the card ratio first, SteamGridDB's order among equals) and tries up to `SGDB_DOWNLOAD_TRIES` (5) in turn; it used to take the first image only and `break`, so one failed download lost the source. A vertical grid is still never landscape or square. SteamGridDB only hosts official sizes (600x900, 660x930, 342x482, 920x430, 460x215, 1024x1024: checked live), so the horizontal request keeps its `?dimensions=460x215,920x430` filter; those are 2.14, never within 5% of the 1.745 card, so wide art always gets edge backdrops.
- **`store` source:** a plugin's `art_urls(appid)` (any subset of vertical/horizontal/icon); core downloads via `download_from_url` and records `'store'`. Class attributes `art_kinds` (default all three) and `art_default_order` (default `('store','sgdb','steam')`; EA App and itch.io use `('sgdb','store','steam')` since their sync already tried SGDB). Only `plugins.plugin_art_kinds()` / `plugin_art_default()` read them; `plugin_js_api()` exposes `art_store` and `art_default` so the editor offers Store only where it works.
- **Defaults:** no saved list and no `art_urls` for that kind -> `None` = the original chain; with `art_urls` -> the plugin's default order, so re-scraping an Epic/GOG game no longer replaces the store's art with SGDB's.
- **UI:** Settings -> Library -> Artwork Sources (`modal_tools.js`: `_renderArtSourcePrefs`, `openArtSourceEditor`): a row per platform (Steam + `window._PLUGIN_API` keys, not `_PLAT_LABELS`, which includes emulators) opening an editor with three lists: custom mousedown drag (native HTML5 drag is unreliable in pywebview), up/down buttons for gamepad, a tick to switch a source off, Reset to Default. `_artDefaultOrder` mirrors `art_source_order`'s defaults; keep them in sync. Changes apply the next time art is fetched.
- The edit modal's art panel labels sources via `_artSourceLabels` (`modal_edit.html`); a new source needs an entry or the raw string shows.

### Card Edge Backdrops (v2026.10.2)
A cover whose shape differs from its card (>5%, same rule as `applyBlurArt`) leaves bars. They used to be a CSS-blurred copy of the cover (a filter on every card, switched off during scroll via `body.is-scrolling`, so blurs popped in when scrolling stopped). Now the bars are painted from colours sampled along the cover's own edges: no filter, nothing to hide or arrive late.
- **Stored per cover:** `games.edge_vertical` / `edge_horizontal` (TEXT). `images.compute_art_edges(img, kind)` returns `'-'` when the cover fits (`ART_CARD_RATIO`: 2/3 vertical, 616/353 horizontal), else `'y'` (wider: bars above/below) or `'x'` (taller: bars at the sides) + 6 comma-separated hex colours for one edge + `/` + 6 for the opposite, already darkened to 0.7 (no `brightness` filter needed). `NULL` = not computed. `save_as_jpg` (the single writer of cover files) computes them; `images.sync_art_edges()` backfills at startup on its own thread (~5 s for 9,000 covers, no-op once done, also covers older-backup restores).
- **Drawing:** `applyBlurArt` (`playdate.js`) takes colours from the card's `data-edge` (Library) or the page-wide `window._ART_EDGES` (vertical only, inlined by `base.html` from `database.get_art_edges()`, keyed by the appid in the image URL; Home and Pick 6, ~130 entries). It sets `--edge-under/--edge-over/--edge-mask` and `needs-edge`; CSS (`library.html`, `index.html`, `pick.html`) draws two stacked gradients on `::before`/`::after`, the second masked to fade across the card. The old blur (`needs-blur`) is the fallback when no colours are stored, the stored direction doesn't match the container, or the value fails `_edgeBackdrop`'s format check (values land in inline styles).
- **Keep in sync:** `ART_CARD_RATIO` and the 5% tolerance mirror what `library.js` passes to `applyBlurArt`. The edit modal's `_patchGameCard` refreshes `data-edge` after art changes.

### Metadata Backfill (`metadata.py`, added v1.9.0; Steam games + retry-on-incomplete v1.9.1)

`metadata_bp` fills what plugins can't provide (tags, review score, categories, any missing genres/dev/pub/release date) by resolving a non-Steam game to a Steam AppID and reusing the Steam scrapers. A Steam game left short of developer/genres/tags by populate/rescrape is re-fetched from its own store page, with PCGW as fallback for what Steam lacks (delisted pages).

- **`_pcgw_infobox(name, session) -> dict | None | _PCGW_UNAVAILABLE`**: `_pcgw_find_page()` tries `_clean_query(name)` as a **literal page title** first (fulltext `list=search` buries the real article, e.g. "Syndicate" -> "Steampunk Syndicate"), then `list=search` gated by `_SIM_PCGW`; then `action=parse&section=0` and parse `{{Infobox game}}` (follows one `#REDIRECT`). Returns what it has: `steam_appid`, `gog_id`, `developers`/`publishers`, `genres`, `categories` (from `taxonomy/modes`: Single-player/Multi-player), earliest `release_date`. **PCGW throttles hard:** `_pcgw_get()` serialises (1.5s gap) and stands down 180s on a 429; `_PCGW_UNAVAILABLE` = "couldn't answer", distinct from "nothing there".
- **`_resolve(name) -> (steam_appid|None, confidence, pcgw_box|None)`** / `resolve_steam_appid(name)` (2-tuple wrapper): PCGW box with a Steam AppID -> `'pcgw'`. Else Steam `storesearch`: an **exact `_norm`-equal name wins outright** (`'confirmed'`, whatever its rank, since search buries the real game under sequels/DLC); otherwise `difflib`: `>= _SIM_CONFIRMED` (0.90) -> `'confirmed'`; `_SIM_MAYBE`..`_SIM_CONFIRMED` -> `'maybe'`, **but if the PCGW box has any `_USEFUL_BOX_KEYS` field the box wins** (`'none'` + box, for delisted classics whose only Steam hit is a wrong fuzzy match), else parked `unconfirmed` with nothing written; PCGW throttled + weak guess -> `'retry'` (record nothing). `backfill_metadata(force=True)` clears a stale `steam_appid` that no longer lands on a Steam page.
- **`backfill_metadata(appid, *, force=False, rerun=False)`** returns a dict for `update_game_data` with **only currently-empty fields** (plugin/populate data wins). Tiers: Steam AppID (its own, or resolved) -> `fetch_store_data`/`fetch_review_data`/`fetch_tag_data`, PCGW box filling what Steam missed (fetched on demand); no Steam AppID but a PCGW page -> dev/pub/genres/categories/release only; **still nothing -> the platform's store page** via `_store_page_metadata()` -> `plugin.store_page_metadata(platform_slug)` (itch.io only; tags filtered to the library's vocabulary). Never touches name, achievements, playtime, art. Outcome -> `games.meta_backfill_fetched` (`0`/NULL never, YYYY-MM-DD, `no_match`, `unconfirmed`); resolved id -> `games.steam_appid` (non-Steam only). `force=True` applies a `maybe` match (implies `rerun`); `rerun=True` re-attempts stamped games (an `unconfirmed` row is always re-resolved, never trusting its parked candidate).
- **`meta_backfill_fetched` gates only the *automatic* startup sweep** (`_METADATA_PENDING_WHERE` = missing dev/genres/tags AND never attempted). Explicit paths use the missing-fields test alone (`_METADATA_INCOMPLETE_WHERE`). Renaming a game (`library.update_game`) resets it to `'0'` and nulls `steam_appid`.
- **Runs from:** startup sweep `sync_metadata_backfill()` (incomplete never-tried games incl. Steam, per-session cap); `bulk_rescrape_games()` for every non-Steam game (after `plugin.rescrape()`, `rerun=True`, shared Steam rate-limit gate); the "Backfill Missing Metadata" bulk op (`op='metadata'` -> `bulk_backfill_metadata`, `rerun=True`, pre-filtered to incomplete rows); `POST /api/metadata/backfill/<appid>` (edit modal "Fill Missing Data", all platforms).

**Also fills (v1.11.2):** `metacritic_score` and `short_description` from the Steam page when empty; for a non-Steam game with no Steam description, `_plugin_description()` asks `fetch_description` and counts it as a fill (so a store exclusive isn't stamped `no_match`); and for **Steam games whose `total_achievements` was never known**, `_achievement_counts()`: the account's progress via `fetch_cheevo_data`, else the public schema total (`scrapers.fetch_achievement_schema_total`, 0 unlocked). `GetPlayerAchievements` answers **403 "Profile is not public" for an unowned game**, which `fetch_cheevo_data` treats as an expected `None` (info log), so an Add Game game would otherwise never get totals. Games with counts are untouched. The edit modal's `setters` map in `fillMetadataFromSteam` must list every field the route can return.

### Card Mouse Actions (v1.11.7)
What each mouse button does on a cover is a user-editable rule list: `state.json` `card_click_rules` = `[{button: left|middle|right|back|forward, click: single|double, action}]`, one per (button, click) pair, `action` one of `launch, tooltip, context_menu, store, open_folder, edit, achievements, community_hub, none`. - **Migration:** the old `require_double_click_launch` setting is gone; `_load_state_unlocked` turns it into a left-double launch rule, keyed on state.json alone and idempotent (a restored old backup is migrated, or just stripped when rules exist, never overwriting the user's rules). Verified in Chromium with synthetic events only; **confirm on a real mouse in WebKitGTK and QtWebEngine**, where the toolkit may swallow them.

- **Actions:** the context menu IIFE exposes `window.pdCtx = {open, steamId, openUrl}`; `store`/`achievements`/`community_hub` reuse its URL logic, `open_folder` calls `/api/open-install-dir/<appid>`, `edit` is `openGameEditor`. Failures show `showLaunchToast`, never silence.
- **Tooltip action:** each page's tooltip IIFE (Library `library.js`, Home, Pick 6) exposes `window.pdCardTip = {show(el, appid), hide}`; the engine hides it on the next `mousedown` or Escape. Hover is off while any rule shows the tooltip (IIFEs read `_CARD_RULES` at load; Library PAGYWOSG quals still show on hover). - **Settings UI:** Settings -> Library -> Mouse Actions (`modal_tools.html`, `saveCardRule`/`editCardRule`/`_saveCardRules`). A button+click another rule already has asks Replace / Swap / Cancel (Swap only when editing) through `confirmThree` (`_dialog.html`, returns `true` / `'alt'` / `false`).

**Gamepad shortcuts.** Gamepad Controls has four rows acting on the game under the focus ring, **unset by default** (`defaultBtn: null`): `sc_store`, `sc_folder`, `sc_achievements`, `sc_community_hub` (A/X/Y already launch/menu/edit). Stored in `button_remaps` (`{rawIdx: action}`), so any raw index works, extras included. `input.js`'s `_onButton` handles them before the core remap (`_SHORTCUT_ACTIONS`, `_focusedGameEl`, which only returns a card in the `content` zone so they never fire in a dialog) via `window.pdRunCardAction`. **Conflicts** (`_grmAssign`): taking a button another action holds clears that action or swaps (when the changed action has a button to give), so a button never has two owners. Confirm / Select and Back / Cancel (`required: true` in `_REMAP_ACTIONS`) are never cleared (a gamepad-only user couldn't recover), only swapped; if the incoming action has nothing to swap, the capture is refused with a toast. No gamepad double-click variants, by design.

### Cached Derived Stats (added v1.10.5)
A whole-library stat too expensive per page load but cheap to recompute fully is cached as a real column and refreshed at the trigger points `database.refresh_duplicate_detection()` established: startup, after a Steam populate, after `bulk_rescrape_games()`, and after any single/bulk edit that could invalidate it, inline with no thread machinery. `database.recalculate_tag_similarity()` (`games.tag_similarity`, a Library/Home sort option) follows this exactly (~130ms for 30,000 games).

**Formula (shared with pick.py's `tag_similarity()`, see Pick 6 Scoring):** per tag, `affinity = liked_rate - library_rate` (fraction of the pool's games carrying the tag); the liked pool is Beaten/Completed (top-50-most-played fallback when none qualify), `library_rate` is the whole Steam library. Finishing a tag proportionally more than it appears is a preference; less is an avoidance (dislike or a genre stuck in the backlog; both read the same). Tags below `MIN_LIBRARY_RATE` (0.02) are excluded (too small a sample; rare tags swing wildly). A candidate's score is `sum(affinity of its tags) / (tag_count + K)`, `K=4` (empirical smoothing, not principled; without it one strongly-liked tag beat several genuinely matching ones).

The negative pool was once `"Won't Play"` (an inconsistent signal, see Database Schema Notes). Live comparison found both surfaced the same core disliked tags, but the library-wide pool tracked avoided tags better and needs no minimum number of `"Won't Play"` games, so it replaced it. An earlier playtime-weighted cosine version let ubiquitous tags dominate ("Action" + "Singleplayer" were 35-40% of one 548-game profile's magnitude); the rate difference suppresses generic tags by itself (a tag equally common in both pools cancels), so no IDF correction is needed.

**Both pools are `platform = 'steam'` only:** not every plugin has a real community-tag vocabulary (Epic's plugin stores review-attribute checkboxes like "Windows" and "Extremely Fun" in `tags`, which surfaced as top "disliked tags" before the filter). A *candidate* isn't restricted to Steam: a non-Steam game's tags are compared against the Steam-sourced affinity dict, unknown tags adding `0.0`.

`tag_similarity` is `NULL` before first computation and for a game with no tags, and sorts last in either direction; a *tagged* game netting exactly zero gets a real `0.0`. This (NULL only for "no signal", never "signal says zero") is the opposite of HLTB's `NULLIF(col, 0)`, so `recalculate_tag_similarity()` special-cases the no-tags branch. Sort defaults to `DESC` via `library.js`'s `_sortDefaultOrder` (also read by `modal_view.html`'s `vmSetSort()`, same page-level script scope); Home shelves already default untouched shelves to `DESC`.

### Playnite Import
Playnite uses LiteDB (not SQLite). `parse_playnite_dates()` proximity-matches (+-8KB) `\x02GameId\x00` and `\x09Added\x00` BSON markers; full parsing needs a LiteDB reader since documents span non-contiguous 8KB pages. Import uses the native file dialog (not upload) because backups can be several GB.

**Two steps, chosen fields (v1.11.2):** `POST /api/import/playnite-dates` only *scans* (background thread -> `parse_playnite_fields()` -> per-field counts for games already in the library; status `ready`; parsed data held in `_playnite_parsed` so a multi-GB backup is read once). `POST /api/import/playnite-apply {fields, mode}` writes the chosen fields (`date_added`, `last_played`, `playtime` -> `playtime_forever`). `fill` only fills blanks (Date Added keeps the *earlier* date, since PlayDate's is just first-seen); `overwrite` replaces. Optional fields (`LastActivity` datetime 0x09, `Playtime` int64 seconds 0x12, int32 0x10 also accepted) are paired **field -> nearest GameId** (+-8KB, closest wins per game), not GameId -> nearest field, so a game lacking the field can't take a neighbour's value; `Added` keeps the original pairing. **The `LastActivity`/`Playtime` layouts are inferred from Playnite's data model and tested only on synthetic files** (get a real `library/games.db` before trusting them).

### Pick 6 Scoring
Six signals: tag similarity (liked-minus-disliked tag affinity, see Key Patterns → Cached Derived Stats for the formula shared with `database.recalculate_tag_similarity()`), review score, staleness (capped 730d), completion bias, playtime (capped 3000min), release recency (capped 10yr). Falls back to top-50-most-played if no beaten games. Weighted random sampling, not sorted top-N.

`pick.py`'s `tag_similarity()` closure rescales its raw affinity score to `[0,1]` via min-max normalization across the *current candidate pool* (not a fixed range) before returning it, since `sig()`'s weighted combination assumes every signal lives in `[0,1]` — its `1.0 - s` direction-flip for a negative weight would otherwise be meaningless against a raw signed score that can go negative. `database.recalculate_tag_similarity()`'s cached column has no such constraint (a sort column doesn't care about scale) and keeps the raw signed value instead.

### Wine/Proton Launch Reliability (Linux)
`runners/wine.py`'s `_build_run()` routes wineboot/winetricks/install/launch through `umu-run` (Steam Runtime container wrapper) whenever it and a real Proton build (`toolmanifest.vdf` present) are available: a bare Proton `wine_bin` can't run standalone (crashes loading `vkd3d`/`wined3d` without the Steam Runtime) and raw Proton wineboot/installer calls repeatedly hung. Applies to every Wine-based plugin.

**Missing-umu guard:** `_resolve_runnable_wine(preferred)` (used by `create_prefix`/`run_in_prefix`/`launch_protocol_url` and `runners/launcher_installer.py`) never returns a Proton binary when `umu-run` isn't on the host: it swaps to a system Wine if one exists, else raises `RuntimeError(PROTON_NEEDS_UMU_MSG)`. `plugins.__init__._augment_launcher_status()` mirrors this onto `launcher_status()` (`proton_without_umu()` downgrades a "ready" badge). `NO_WINE_MSG`/`PROTON_NEEDS_UMU_MSG` carry a "on the host, not Flatpaks" suffix under `IN_FLATPAK`.

**Already-running-session:** a *second* `umu-run` against a prefix with a live session deadlocks (`do_lock_file_wait`) instead of joining it; `UMU_CONTAINER_NSENTER=1` didn't hold up (see PLUGINS_STATUS.md, Ubisoft Connect, 2026-08-26 part 2). `launch_protocol_url()` and `run_in_prefix()` check `_prefix_has_running_process()` first and branch:
- **no live session** -> full container (`_build_run` -> `umu-run` for Proton).
- **live session + `restart_session_if_running=False` (default)** -> deliver into it with a plain `wine`/`wine start` (no container; for Proton `build_proton_env` supplies lib paths, not umu-run). A deep link is accepted by the running launcher, and for a game prefix the live session is another game that must not be killed. **The Proton half is provisional: confirm live that it reaches a umu-started session; a launcher that doesn't take the link passes `restart_session_if_running=True`.**
- **live session + `restart_session_if_running=True`** -> `end_prefix_session()` (`wineserver -k -w`), then cold `umu-run`. Only Ubisoft Connect passes this (its Chromium UI won't accept a `uplay://` link while running; it re-forwards on startup). Reliable on GE-Proton, official Proton, `UMU-Proton`.

**Concurrency:** the check/kill/relaunch sequence must not race itself (Waitress has 8 threads; three rapid Epic launch clicks spawned three `umu-run` containers, orphaned `wineserver`s and crashed `pressure-vessel`). `_get_prefix_lock(prefix_path)` is one `threading.Lock` per absolute prefix path, held around the whole decision in both functions, not the launched process's lifetime (worst case a second request waits ~10s for `end_prefix_session()`).

**`WINEPREFIX` for a launched game is `<prefix>/pfx`**, not `<prefix>` (Proton's `compatdata/<id>/pfx/` layout); `list_prefix_processes(prefix_path)` matches both.

**Flatpak: process scans must read the *host's* `/proc`.** `runners/sandbox.py` runs Wine/Proton/umu-run on the host via `flatpak-spawn --host`, so from inside the sandbox a `/proc` scan sees only PlayDate and session/running-game detection silently no-ops (and `end_prefix_session()`'s poll is meaningless, hence its `wineserver -k -w`). `list_prefix_processes()` branches on `IN_FLATPAK` (`_list_prefix_processes_host`, a `flatpak-spawn --host sh -c` script); `/api/game-running`'s `pgrep` goes through `host_run`. Any new Linux process-existence check must go through the host too. **Windows/macOS are unaffected: the Wine-prefix/session subsystem is Linux-only.**

**Wayland:** `_prefer_native_wayland()` drops `DISPLAY` when `WAYLAND_DISPLAY` is set, for plain (non-Proton) Wine only (Proton forces native Wayland itself); without it a self-contained Wine fell back to XWayland under KDE Plasma with slow/unregistered clicks.

### Steam Deck evdev gamepad reader (`gamepad_reader.py`)
Used in a Deck session (`config._is_steam_deck_session()`); reads `/dev/input/event*` directly and pushes a W3C-"standard"-shaped pad to the page as `window._pdPad` (`main.py` step 6b). `find_gamepad()` takes the first node with `BTN_SOUTH`, preferring an "Xbox"-named one (may be an external pad, not Steam's virtual "Microsoft X-Box 360 pad"). The two have **different axis layouts**, so `GamepadReader._configure()` reads each device's layout and real ranges (`EVIOCGABS`): triggers on `ABS_BRAKE`/`ABS_GAS` vs `ABS_Z`/`ABS_RZ`, right stick on `ABS_Z`/`ABS_RZ` vs `ABS_RX`/`ABS_RY`, signed vs unsigned sticks, all normalised from min/max (`_norm`). Any new pad type is a new layout to check with `evtest`.

**Desktop Linux opt-in (v1.12.0): Settings > Gamepad > "Read controller directly"** (`state.json` `evdev_gamepad`, `config.evdev_gamepad_available()`: Linux, not Deck, not Qt). Exists because WebKitGTK's libmanette can apply a wrong mapping PlayDate can't see under (8BitDo Ultimate 2: triggers sharing stick axes, dead d-pad; Qt's raw data was fine). Needs a restart. `main.py` decides `_EVDEV_PAD` before Flask starts (GTK only, never Qt: the hand-off uses `GLib.idle_add`, which never fires under Qt) and sets `PLAYDATE_EVDEV_PAD=1` **and clears it otherwise** (a restart's child inherits the parent's env, and a stale flag made a Qt run lose its gamepad); `inject_config_status()` turns it into `window._EVDEV_PAD`, then step 6b arms `GamepadReader(desktop=True)`. That mode prefers a real pad over the virtual one and uses `Name (Vendor: xxxx Product: yyyy)` as the pad id; the page treats `_pdPad` like the Deck path (`input.js` `_DECK_SESSION` = Deck or `_EVDEV_PAD`). The pad arrives already standard-ordered, so layouts are not applied (`pdStandardizeGamepad` skips `_pdPad`); paddles beyond the 17 standard buttons aren't forwarded; only the Xbox-driver and ABS_BRAKE/GAS axis layouts are understood. **Not verified: the real GTK window path under pywebview, and live press values.**

### Pads with no "standard" mapping (v1.11.7)
When the browser has no W3C mapping (`gp.mapping === ''`), Linux hands over raw evdev order; for an Xbox-style pad that is axes LX, LY, **LT**, RX, RY, **RT**, HAT-X, HAT-Y and buttons A, B, X, Y, LB, RB, Back, Start, Guide, L3, R3, which misreads as a standard pad. `static/js/gamepad_layout.js`'s `pdStandardizeGamepad()` rewrites such a pad into a standard-shaped copy (`_pdNormalized`, `_pdLayout` = where the layout came from). Every reader goes through it (`input.js` poll loop, `modal_tools.js` `_firstGamepad()`), so button numbers agree everywhere; Diagnostics passes `raw = true` for its raw readouts. It never touches the Deck's `_pdPad`, and leaves a standard-mapped pad alone **unless the user saved a custom layout (`kind: 'map'`) for it** (the chooser then shows Auto / Custom / Set up custom layout, and the wizard starts from the identity `PDLayout.STANDARD_MAP`).
- **A layout is an SDL mapping string** (`a:b0,leftx:a0,lefttrigger:a2,dpup:h0.1,...`): `bN` button, `aN` axis (`+aN`/`-aN` one direction, `aN~` inverted; a full-range trigger rests at -1), `hN.M` hat bit (1 up, 2 right, 4 down, 8 left; hat 0 = the pad's last two axes). `PDLayout.parse` yields the standard 17 buttons + 4 axes; unused raw buttons follow as 17+ in raw order (bindable in Gamepad Controls). `PDLayout.fits` rejects a layout reading an index the pad lacks or a hat overlapping a stick axis.
- **Which layout, first match wins:** (1) the user's saved choice per controller id (`state.json` `gamepad_layouts` = `{id: {kind: 'standard'|'map', map?, style?, names?, shape?, parts?}}`, `config.normalize_gamepad_layouts`, `window._GAMEPAD_LAYOUTS`; `'auto'` is never stored); (2) the bundled database entry for the id's USB vendor/product that fits; (3) the Xbox-style raw order, recognised by both trigger axes (2 and 5) resting at -1 with >= 8 axes and >= 11 buttons (latched per pad); (4) none. Vendor/product come from the id: `Vendor: 2dc8 Product: 310b` (Chromium/Qt) or `2dc8-310b-Name` (Firefox); a plain name gets no lookup. **The signature check (3) can fail at startup** (an unmoved axis may report 0), so database/saved paths must not depend on rest values; the converter treats a full-range trigger axis as released until it has reported non-zero (`axesSeen`).
- **Database:** `static/data/gamepad_layouts.json` (~150 KB, 560 controllers), generated by dev-only `tools/build_gamepad_db.py` from [SDL_GameControllerDB](https://github.com/mdqinc/SDL_GameControllerDB) (zlib licence file alongside), Linux entries only, keyed `vvvv:pppp`, fetched lazily. When several layouts fit one product, `restScore` picks the one whose triggers rest at -1 and sticks don't. Windows/macOS entries are not included (their raw orders differ).
- **Gamepad Setup** (formerly Gamepad Diagnostics; code names kept: `gamepad-diag-modal`, `openGamepadDiag`, `_gpd*`) holds the layout chooser, button names, wizard and a "Test controller (live input)" view (`gpdToggleLive`, `window._gpdLive`). **Gamepad input is suppressed only while the live view is showing or the wizard / name editor is open** (`input.js` `_pollLoop`: `recording || liveOn`); holding Back (Confirm if no Back is set) for `GP_DIAG_CLOSE_HOLD_MS` hides the live view (never while the wizard/editor is open, where B may be what's recorded). Escape is ignored in the same two situations. Otherwise the pad navigates it like any modal.
- **Dependent buttons:** "Gamepad Controls" and "Gamepad Setup" are dimmed and toast on click while gamepad input is off (`openGamepadDependent`, `base.html`); CSS dimming plus a guard, never `disabled`.
- **Layout chooser** (`_gpdRenderLayout`, `gpdPickLayout`) offers only choices that change something: Auto, database layouts / Xbox-style order **only when they differ in behaviour from Auto** (`PDLayout.sameMap`, `info().autoMap`), Custom (saved), Standard **only if already chosen**, and "Set up custom layout...". A second row picks the label style (Xbox, PlayStation, Nintendo, Other; `PDLayout.setStyle`, kept when the layout changes; picking the vendor-id guess clears the saved style). Re-showing the choices row must set `display:flex`, not clear it (clearing dropped the gap and hid the focus ring). The three Setup screens use a 12px button gap and lift the focused button (`position:relative; z-index:2`).
- **Layout wizard** (`static/js/gamepad_wizard.js`, markup in `modal_tools.html`, z-index 1003 above Diagnostics at 1002): one step per placed control, each highlighted on the SVG drawing, waiting for it on the real pad; saves an SDL mapping string (`kind: 'map'`). Starts from the layout in use (skipped steps keep their source); saving requires Confirm recorded plus a d-pad or left stick (Back is optional, also in Gamepad Controls). Detection reads the **raw** pad (`_firstGamepad(true)`). Recording: button `bN`; stick axis `aN` (`aN~` if pushing right/down reads negative); trigger axis waits for release, `aN` if it rests at -1 else `+aN`/`-aN`; d-pad as four buttons, a hat, or half axes. No "extras" step (the converter keeps unused raw buttons). **Rest reports:** an unmoved axis reads 0 and often first jumps straight to -1, so on the trigger step an exact 0 -> <= -0.99 change only updates the baseline (`movedAxis(..., restReports)`); without it the wrong axis was recorded on the 8BitDo (LT axis 2, RT axis 5). "Let go" is also decided by 600 ms of quiet; after 1.5 s the wizard names what it's waiting on. Diagnostics' hold-B-to-close is disabled while it is open; Escape/Cancel exit. Only sources recorded **in the current run** (`W.fresh`) count as taken by another control, and a new recording evicts the old layout's entry on the same button/axis. A stick or trigger step that sees no free axis move falls back to an axis another control took (`moved()` in `listen()`), so shared axes can be recorded (behaviour of such a pad in use untested).
- **Custom controller drawing (wizard editor, v1.12.0):** pick a **body** (`BODIES`: Xbox-style, PlayStation-style, rounded retro, wide six-button, square box, N64, blank; outline path + `starter()` parts), then add/select/remove/**drag** parts with the mouse (pointer events, `toSvg()` to the 400x244 viewBox; changing body after editing asks via `confirmCustom`). Part types: `dpad` (max 1), `stick` (max 2), `face`, `shoulder`, `trigger`, `center`, `other` (typed label). Saved as `shape` + `parts` (`[{type, x, y, role?, label?, raw?}]`), validated by `config.normalize_gamepad_parts` (type whitelist, coords in the viewBox, `role` only on `face`, label <= 12 printable chars, `raw` 0..255, 40 parts max).
  - **The SDL field a part records is derived from type and position, not stored** (`derive()`): first bumper/trigger per side (x < 200 = left) is the standard one, more are extras; sticks left then right by x (a lone stick is left); center buttons by x are Back, Guide, Start (1 = Start, 2 = Back/Start, 3 = Back/Guide/Start, more = extras); a `face` with `role` (`a` Confirm, `b` Back, `x` Menu, `y` Edit) records that field, none = extra; `other` = extra. Sources are keyed by part (`p3`, `p3.up`, `p1.click`), so changing a face button's role only changes which field it feeds (`slotsOf()`).
  - **Steps** walk parts in list order (`stepsFor`: d-pad 4 steps, stick x/y/optional click, else 1). Afterwards face buttons are clickable to set Confirm/Back/Menu/Edit/Extra (xbox/ps/retro starters pre-assign by position, other bodies need it by hand). Extras keep their raw button in `raw`; an `other` part's label is also written to `names[raw]`.
  - **Live view** draws the saved drawing, else `PDWizard.drawingFor()` (PlayStation-style pad -> `ps`, layout without `leftx` -> `retro`, else `xbox`, minus controls the layout lacks; in-memory `field` honoured by `derive()`, never saved). Elements carry `data-btn` (converted index) or `data-raw` (resolved via the converted pad's `_pdRaw`), so it reads the *converted* pad. `PDLayout.save` drops `shape`/`parts` whenever a layout is chosen from the chooser (names and style kept), so only the wizard sets a drawing and Auto restores the default. Not stored per part: the raw source.
- **Custom button names** (Diagnostics > Button names > Rename buttons..., `gpdOpenNames`, `gamepad-names-modal` z-index 1003): a text box per raw button (12 chars), placeholder = the style's name, pressing a button highlights its row. Saved as `names` in `gamepad_layouts[id]`, **keyed by raw button number** (a physical button's raw number never changes, the converted one does). `_activeBtnLabels(id)` maps converted -> raw via `_pdRaw` and applies names last, after XY-swap compensation (`noCustom` gives plain names). Plain buttons only (not axis triggers, sticks, hat d-pad).
- **Bindings on extra buttons follow the button:** `PDLayout.save` translates each `button_remaps` entry at 17+ to the same physical button through `_pdRaw` before/after (`keepExtraBindings`), dropping one whose button became a standard control. Not covered: a layout that changes by itself (database arriving late, signature check succeeding after a trigger press).
- **Live drawing in Diagnostics** (`_gpdUpdateDrawing`): built once per shape + style; `PDWizard.liveUpdate(svg, convertedPad)` toggles `gpw-live` on `[data-ctl]` groups (triggers > 0.15, rest > 0.5; L3/R3 light the stick ring) and moves `[data-stick]` thumbs. Only two raw lines remain besides it (All axes (raw), All buttons (raw), where extras show).
- **Leaving the live view without Back:** `input.js` hides it on a 1.5 s hold of Back (`_rawFor('b')`, honours remaps, ignores the default index when the layout has no `b:`), else Confirm. Live view only, never an app-wide "hold Confirm = Back".
- **Label styles** (xbox, ps, nintendo, other) decide face-button symbols and names (`_activeBtnLabels` / `_faceButtonColor`); default from vendor id (`054c` PlayStation, `057e` Nintendo, else Xbox).
- **Not verified:** database entries for other pads (they follow SDL's Linux order, which matched the one real pad), and whether WebKitGTK needs X/Y swapped for a converted pad (`pdGamepadXYSwapped()` compensates for libmanette on pads it maps itself; the converter outputs spec order and does not swap).

### Qt/QtWebEngine Alternate Renderer (Linux)
Linux's default renderer is WebKitGTK with compositing/DMA-BUF forced off (`WEBKIT_DISABLE_COMPOSITING_MODE`/`WEBKIT_DISABLE_DMABUF_RENDERER` in `main.py`); the tradeoff is choppy grid scrolling on NVIDIA's proprietary driver under Wayland (WebKit bug #262607, WONTFIX). Qt/QtWebEngine (Chromium) is an opt-in alternate renderer for that case, confirmed to fix it.

**Availability vs. relevance are separate gates:** `config.qt_renderer_available()` (Linux, not a real Deck session) controls whether Settings' Renderer toggle appears, for source and Flatpak. `config.qt_renderer_relevant()` (`WAYLAND_DISPLAY` set **and** `/proc/driver/nvidia/version` exists, i.e. the proprietary driver) only gates the "you probably want this" hint on the library page.

**`main.py` renderer resolution** (before the GTK probe and `import webview`): `_FORCE_QT` (`PLAYDATE_FORCE_QT=1`, the Flatpak Qt variant's `finish-args`) or `state.json`'s `renderer` (source installs only) decides `_WANT_QT`; an import probe (`from qtpy.QtWebEngineWidgets import QWebEngineView`) decides `_USE_QT`, falling back to GTK on failure and resetting `renderer` to `"gtk"`. Deck sessions force `_WANT_QT = False` unconditionally: the Deck's evdev reader needs a GLib main loop (`GLib.idle_add`) that never fires under Qt, freezing gamepad input; this override is the real backstop whatever the UI or a hand-edited `state.json` says. When `_USE_QT`, `PYWEBVIEW_GUI=qt` and `QTWEBENGINE_CHROMIUM_FLAGS=--no-sandbox --no-sandbox` are set explicitly: **don't rely on pywebview's qt.py for the sandbox flag**, it only sets it for a hardcoded distro allowlist and otherwise crashes silently (SIGTRAP in `QWebEngineProfile`'s constructor, no Python exception).

**`qt_webview_patch.py`** monkeypatches pywebview's `webview.platforms.qt` (as `gtk3webview_patch.py` does for GTK): `WebView.wheelEvent` gets a 3x delta multiplier since Chromium's default wheel scroll is slower than WebKitGTK's. Loaded in `main.py`'s `_USE_QT` branch right after `import webview`.

**Smooth scroll doesn't animate under QtWebEngine** (`scrollIntoView({behavior:'smooth'})`, upstream Chromium limitation). `input.js`'s `_animatedScrollIntoView()` is a renderer-agnostic `requestAnimationFrame` replacement (library grid and home shelf rows, vertical) using `_scrollableAncestor()` (handles window scroll and list view's `#list-pane`); Pick 6 never scrolls and is untouched. `_animatedScrollIntoViewX()` is the horizontal counterpart for home shelves; `_scrollableAncestor()` takes an axis (`'x'`/`'y'`).

**Source-install toggle** (`qt_renderer.py`, non-Flatpak Linux): background-thread install/uninstall routes shaped like `updater.py`'s self-update. It must be `pip install --force-reinstall PyQt6 PyQt6-WebEngine QtPy`, not `pywebview[qt6]`: the venv is `--system-site-packages` (for GTK bindings), so on a distro with a system PyQt6 a plain install pulls only `PyQt6-WebEngine` with its own Qt6 libs, an ABI mismatch that SIGTRAPs the moment QtWebEngine is used. `--force-reinstall` puts a matching PyQt6 in the venv's own site-packages, which win.

**Flatpak: two separate app-IDs, not a toggle in one build.** `io.github.robbyratpoison.PlayDate.Qt` (`flatpak/io.github.robbyratpoison.PlayDate.Qt.yml`) builds against `com.riverbankcomputing.PyQt.BaseApp` on `org.kde.Platform`/`Sdk` (the GTK manifest uses `org.gnome.Platform`); QtWebEngine is build-time-only in Flatpak, so no in-app download-and-switch. Gotchas specific to a `base:` manifest:
- The CPython tag for the hand-built `_tkinter` (neither runtime ships Tcl/Tk) must match *this* runtime's Python, not GNOME's (check with `flatpak run --command=python3 org.kde.Sdk//6.11 --version`; was 3.13.13 vs 3.13.14).
- `qtpy` must be listed in `requirements-flatpak-qt.txt`; the BaseApp doesn't bundle it.
- tcl/tk's `chmod u+w` workaround must be scoped to that module's own files (`-maxdepth 1 -name 'libtcl*.so*'`), not a blanket `/app/lib` sweep: a `base:` mounts the base's read-only `/app` into every module's build.
- Gamepad needs `--filesystem=/run/udev:ro` on the Qt manifest only (Chromium's backend needs the udev database; netlink is unsupported in the sandbox, `flatpak/flatpak#961`).

**The Renderer toggle drives a real app swap on Flatpak:** `qt_renderer.py`'s `_do_flatpak_swap()` downloads the other variant's release asset (`updater._running_flatpak_app_id()` reads `/.flatpak-info`), copies the whole data dir into `~/.var/app/<id>/data/playdate` (both manifests grant `--filesystem=home` for this; a shared/symlinked data path was rejected, see the `project_qtwebengine_rendering_investigation` memory), installs the new variant, uninstalls the old (they don't merge into one dock entry), and relaunches. The confirm() warns that a pinned shortcut to the old variant breaks (no portable way to migrate a pin). Relaunch uses `sleep 2; exec flatpak run ...` (also used by the Deck rungameid branch and `updater.py`'s plain relaunch), else the new process's `_port_in_use()` check runs before the old one frees port 5000 and shows the "already running" screen.

**`updater.py` is variant-aware:** `_do_update_check()` matches release assets by a `-qt.flatpak` filename marker against the running variant, so a normal update never swaps renderers, and caches the other variant's URL (`flatpak_url_other_variant`) for the swap.

**CI**: `build-windows.yml`'s `build-flatpak` and `flatpak-cache.yml` build the GTK and Qt variants as a matrix with `max-parallel: 1`, because both legs append to the same ostree repo and GitHub Release (concurrent legs risk a stale "restore from gh-pages" or an asset-upload race). **Not exercised for real:** beta/rc tags never publish to gh-pages, so the two-variant shared ostree repo is untested until the first stable release.

**`--system`-scope Flatpak installs can't self-update** (`flatpak install --system` needs interactive Polkit `auth_admin`, which a `flatpak-spawn --host` background process can't satisfy; confirmed live: `Flatpak system operation InstallBundle not allowed for user`). `GET /api/flatpak-scope` (`updater._flatpak_install_scope()`, reads the *running* copy's `[Instance] app-path` from `/.flatpak-info`, since both scopes can coexist) lets `handleUpdateBtn()` in `base.html` show an amber warning; a failed `--system` update keeps the bundle, sets `fix_command` on `_update_dl_state` to `sudo flatpak install --system -y --reinstall "<bundle>"`, and the failure screen shows it with a Copy button. `flatpak update <app-id>` was rejected as the suggestion (reports "Nothing to update"). The README recommends `--user`.

## Plugin System

Non-Steam library sources are optional plugins in `<id>/` subdirectories. See `PLUGINS.md` for the full developer guide. Key points:

- **Plugin storage:** installed plugins live in the writable `plugins._user_plugins_dir()` (`BASE_DIR/plugins/`), separate from the legacy bundled `plugins/` next to `plugins/__init__.py` (the same directory for a source checkout; for Flatpak/frozen builds only the writable one survives an update). `load_all()` scans both, migrates anything left in the legacy location into the writable one (`_migrate_legacy_plugin_dirs`, self-terminating), and is safe to call repeatedly (skips ids already in `_plugins`). Any folder with a `plugin.json` is auto-discovered.
- **Official (first-party) plugins** (GOG, EA App, Epic Games, Humble Bundle, IndieGala, itch.io, Ubisoft Connect, Battle.net, Rockstar Games, Amazon Games, Legacy Games, Xbox / Game Pass for PC) are their own GitHub repos listed in `plugins.OFFICIAL_PLUGINS` (`{id, name, source, platform_status}`) and installed like any third-party plugin. There is **no "beta" tier**: maturity is each entry's per-platform `platform_status`. `reinstall_configured_official_plugins()` runs once at startup, *before* the first `load_all()`/`register_blueprint` (Flask refuses new blueprints once it has served a request), and re-fetches a missing entry *only if* there is evidence of prior configuration (a saved token in `config.json[plugin_id]` or launcher config in `config.json['launchers'][plugin_id]`, both cleared by a real uninstall), so it never resurrects a deliberate removal or installs something nobody configured (that's the Plugin Catalog's opt-in).
- **`platform_status`:** `{windows, linux, mac} -> 'working' | 'untested' | 'broken'`, from real reports, not "should work in theory". `GET /api/plugins/catalog` resolves it against `_current_platform_key()` and buckets it for the Plugins modal's Working/Untested/Broken sections. Mirrored in each `plugin.json`, but `plugins/__init__.py`'s copy is what core reads.
- **`min_core_version` in `plugin.json`** (optional): if newer than `config.__version__`, `load_all()` skips the plugin (recorded in `_incompatible_plugins`, `GET /api/plugins/incompatible`, shown as a "needs PlayDate X.Y.Z" badge, still uninstallable; the uninstall checks both locations since it was never in `_plugin_paths`).
- **Only raise a plugin's `min_core_version` together with a bump to its own `version`, never alone.** Raising it alone retroactively marks the already-shipped version incompatible for everyone on an older PlayDate. Only a genuinely new plugin release that assumes new core behaviour justifies gating (2026-08-27: GOG/Humble/itch.io/IndieGala's lone bump was reverted).
- **`min_core_version` is also enforced at install/update time:** `_install_plugin_zip()` (zip upload, `POST /api/plugins/install-from-github`, the Update button) rejects a plugin whose `min_core_version` exceeds the relevant PlayDate version with a user-facing `ValueError`. Its optional `target_core_version` is used only by the "update PlayDate and plugins together" flow (`_doInstallUpdateWithPlugins()` in `base.html`), which installs plugin updates *before* the core update. `GET /api/plugins/check-updates` never suppresses `update_available` for a mismatch; it adds `requires_core`, and the gate stays at install time. `_checkPluginUpdates` (`modal_tools.js`) keeps a gated plugin in `window._pendingPluginUpdates` (the combined flow still updates it) but shows a non-clickable "vX.Y.Z · needs PlayDate A.B.C" note and lights only the Plugins-section dot, not the global hamburger dot (reserved for directly actionable updates).
- **Jinja2 globals:** `has_plugin(id)`, `plugin_fragments(slot)`, `platform_labels()`, `plugin_js_api()`.
- **`window._PLAT_LABELS`** (`base.html`): platform key -> display label; use it instead of hardcoded dicts (core: `steam`, `epic_games`, `ea_app`, `ubisoft`; plugins add theirs).
- **`window._PLUGIN_API`** (`base.html`): platform key -> `{uninstall_url, scrape_url, scrape_method, store_url, store_label, appid_label, sync_label}`. Core templates use it; no platform-specific branches in core code.
- **Management UI:** hamburger -> Plugins; install via zip, GitHub URL, or the Plugin Catalog (`GET /api/plugins/catalog`: `OFFICIAL_PLUGINS` not currently loaded); uninstall with optional game removal. `uninstall_plugin()` also clears the in-memory `_plugins`/`_plugin_paths`/`_plugin_manifests`.
- **Top-bar progress button (v1.12.1):** `base.html` polls `/api/bulk-op/status` every 15s for 13 minutes after load, then once a minute, so late-starting jobs show. A plugin can drive it by claiming `library._bulk_op_state` (Epic's listing repair does; if the slot is busy it runs without a bar).
- **Restart notice:** `#plugins-restart-notice` (`_showPluginRestartNotice()` on every install/update/uninstall success, not on modal open) has "Restart Now" -> `_restartPlayDate()` -> `POST /api/restart` (`updater.py`); `_relaunch()` reuses `perform_update()`'s relaunch strategy with a ~2s child delay so the old process frees port 5000, then `os._exit(0)`.
- **GitHub install:** `POST /api/plugins/install-from-github` takes `{url}` (any `github.com/owner/repo` form), fetches the latest release zip (else zipball) and installs via `_install_plugin_zip(raw_bytes)`.
- **Update checking:** `GET /api/plugins/check-updates` checks GitHub for each plugin whose `plugin.json` has `"source": "github:owner/repo"`, compares semver to `version`, 6-hour per-plugin cache (`_plugin_update_cache`). The frontend driver `_checkPluginUpdates()` (`modal_tools.js`) fills `window._pendingPluginUpdates`, lights the Plugins hamburger dot, and **returns `{standalone, gated, names}`**. It is called from the Plugins modal opening, `initUpdateUI()` on every page load, and `_runUpdateCheck()`, which **awaits** it so a plugin-only update is reported instead of "You're up to date!". Don't make that fire-and-forget.
- **Bulk plugin updates:** an "Update All" button (`#plugin-update-all-btn`) shows when >=1 plugin has a *standalone* update; `_updateAllPlugins()` installs sequentially with a `_PLUGIN_UPDATE_GAP_MS` (500ms) pause (each install is 1-2 unauthenticated `api.github.com` calls: 60 req/hr plus a burst limit). `_doInstallUpdateWithPlugins()` uses the same pause.
- **`launch_game(appid)`:** core `/api/launch/<appid>` dispatches non-Steam platforms to `plugin.launch_game(appid)` by `platform`; 501 if no plugin claims it. When a game must install first, return `{"status": "installing", "install_poller": "<js_fn_name>", "message": "..."}`; core calls `window[install_poller](appid)` if it exists. No platform-named flags like `gog_install`.
- **`rescrape(appid) -> dict | None`:** optional; `bulk_rescrape_games` calls it for non-Steam games; returns a dict for `update_game_data(**meta)` (incl. `meta_fetched`, `cheevos_fetched` if applicable) or `None`.
- **`resync_installed()`:** optional; re-checks installed flag/install_path for every game on the platform. `bulk_rescrape_games()` calls it once after the sweep for each non-Steam platform it touched (rescraped metadata, e.g. a content_id, can newly make detection succeed, and no filesystem event would trigger it); `backup.py` calls it after a restore. **A missing launcher/prefix/config means "nothing installed" (clear every stale `installed=1`), not an early `return`**, or a deleted prefix leaves the badge and Open Folder disagreeing forever.
- **`runners.watcher.PluginInstallWatcher`:** event-driven install-status watcher shared by Wine-based plugins (like Steam's `steamapps` watcher in `utils.py`). If `start(watch_path)` is called before the path exists, it retries every 30s until it does.
- **`fetch_description(appid, platform_id) -> str | None`:** optional; used by `/api/game-description/<appid>` for non-Steam platforms (plain text, or `None`); core falls back to Steam.
- **`store_page_metadata(url) -> dict`:** optional; `metadata.backfill_metadata()`'s last tier for a store exclusive (no Steam, no PCGW): scrape genres/tags/release from the store HTML. Only itch.io implements it, filtering tags to the library's existing vocabulary.
- **`scan_junk() -> list[{appid, name, reason}]`:** optional; Blacklist Manager's "Find Library Junk" -> "Deep Plugin Scan" (`GET /api/steam-junk-scan/deep`). Re-check untouched imported games against the plugin's *current* import filters and return the non-games (DLC, soundtracks, dev kits); may call the store API read-only; `[]` if not connected. Core dedupes against the blacklist + junk whitelist. Opt-in (button) because a full re-check is slow. The fast title-pattern scan (`_JUNK_PATTERNS` in `library.py`) runs on modal open for **all** platforms with no plugin support.
- **`art_urls(appid) -> {'vertical'|'horizontal'|'icon': url}`:** optional (v1.11.2); the platform's own art for the Artwork Sources "Store" option (see Cover Art Pipeline). Any subset, `{}` if unavailable; core downloads/converts (`download_from_url` also accepts local paths). Class attributes: **`art_kinds`** (art types genuinely covered, default all three; GOG is `('vertical',)`) and **`art_default_order`** (default `('store','sgdb','steam')`). Needs a plugin `version` bump but **not** `min_core_version` (older cores ignore it). Implemented in Epic Games, GOG, Xbox, Legacy Games, Ubisoft, EA App, IndieGala, itch.io; live-tested only for GOG, the rest with stubbed network calls.
- **`date_import_url` (class attr, str):** optional external orders/activation page for the Tampermonkey date-import script; core returns the selection's URLs as `date_import_urls: [{url, label}]` and the frontend opens each in a new tab.
- **`launcher` in `plugin.json`:** `{"required": true, "name": "...", "exe_name": "..."}` or `{"required": false}`; core drives the launcher config UI from it.
- **Launcher config:** `GET/POST /api/launcher-config/<platform_id>` stores `{wine_bin, prefix, mode}` under `config.json["launchers"]`; GET adds `wine_bin_detected` from `runners.wine.find_wine_binary()`.
- **`launcher_status()`:** optional, returns `{"available": bool, "detail": str}`; run at startup (3s delay), cached in `_launcher_status_cache`; `GET /api/plugins/launcher-status`, `POST .../<platform_id>` re-runs. Plugin cards show a green "Launcher ready" badge or amber warning + "Configure Launcher" when `launcher.required`; the config panel pre-fills the Wine binary.
- **`manage_ui()` button actions:** `call` (JS function by name), `post`, `open_url` (system browser), `oauth_popup` (`main.py`'s `open_auth_popup()`, in-app WebKit login), `oauth_paste` (paste-a-value modal, no popup). The `onclick` is built with `JSON.stringify` and must go through `escHtml()` (done in `_buildManageBlockHtml`, `modal_tools.html`); don't bypass it.
- **Login popups blocked by bot detection:** several plugins (Amazon Games, Rockstar, itch.io, Epic Games) pair `oauth_popup` with an `oauth_paste` button plus instructions, because the embedded popup can stick on a Cloudflare/captcha page (confirmed live on itch.io and Epic): sign in in a real browser, paste the code/key/cookie. Both funnel through the same `callback_endpoint`. Don't assume `oauth_popup` alone suffices behind Cloudflare. EA App is `oauth_paste`-only (user pastes the `access_token` from EA's token URL).
- **EA App install/launch/uninstall are deliberately minimal: just open EA App, like Lutris.** A native downloader, an LSX/OOA/Denuvo launch bypass and an offerId `origin2://` hand-off were all tried and removed (2026-08-27, PLUGINS_STATUS.md): legacy pre-DIP manifests have no resolvable exe, and EA Desktop rejects the hand-off for reissued classics ("belongs to another user"). Install *detection* (`manifest.find_manifest_path_by_content_id()`/`find_install_dir_by_name()`) stays. Don't resurrect native launch without re-reading that history.
- **Duplicate detection:** `database.auto_detect_duplicates(platform_priority=None)` matches games across platforms by normalized name and marks the lower-priority copy `duplicate_of` the higher one (Steam is just priority 0 by default; Epic+GOG with no Steam copy still dedupes). `refresh_duplicate_detection()` wraps it with the saved priority + plugin platforms and cache invalidation; it runs after a Steam populate, after `bulk_rescrape_games()`, and at startup (covering plugin syncs from a previous session). `POST /api/detect-duplicates` is manual. **The platform priority order always decides which copy is shown; a hand-made link never overrides it (v1.11.2, deliberate).** The edit modal's "Duplicate of" row (`POST /api/game/<id>/set-duplicate`, searches the library excluding the game's own platform) writes a manual link (`duplicate_auto = 0`) and re-runs detection; `_align_manual_duplicate_links()` re-points manual links from the lower-priority copy to the higher, flipping reversed ones (and re-flipping when priority changes), never leaving the pair pointing at each other. Auto links are cleared and recomputed each run; manual ones persist, so a hand link only matters when names differ. Unlinking a name-matched pair doesn't stick; the escape hatch is Settings -> Library -> "Hide duplicate entries" (`hide_duplicates`). Same-platform links are left to Find Duplicate Entries. **Hiding is relative to the active filter (v2026.10.2):** a game owned on several stores shows once, as its highest-priority copy that passes the current filter. `database.hide_duplicates_where(where, params)`, applied last by Library, Home shelves and Pick 6, hides a copy when a higher-ranked copy passes the same finished WHERE clause (exclude the top copy and only the second shows; exclude a middle one and the top still hides the last). This needs each group to be a **star around the shown copy** (`duplicate_of` points straight at it), so `_flatten_duplicate_links()` runs at the end of `auto_detect_duplicates()` (the pairwise pass left chains like Humble -> Epic -> Steam). The clause is repeated inside two index-friendly subqueries (shown copy by appid, others by `duplicate_of`; one OR'd lookup scanned the table, 1.8 s) on the other copies' rows, where unqualified columns resolve to them, and its params are tripled. Consequence: per-copy fields differ, so a game finished on Steam can appear under "Never Played" via its Epic copy. Plugins must not add their own duplicate detection routes.
- **Platform validation:** `hidden_platforms` and `platform_priority` entries match `^[a-z][a-z0-9_]*$` (no allowlists; values come from the DB and plugin registrations). `_plat_order` derives from `platform_labels()` (core + plugin labels).
- **Steam is not a plugin.** It is the core.

## Frontend JS

**`playdate.js`** — loaded globally on every page. Shared utilities: `escHtml(s)` (HTML-escape for safe `innerHTML` use), `fmtHours(minutes)`, SQL syntax highlighter, `safeLocal`/`safeSession` (storage wrappers). Always use `escHtml()` instead of manual `replace()` chains when inserting user/API data into `innerHTML`.

**Custom dropdowns:** Never add a native `<select>` without calling `initCustomSelect()` on it. Native selects create OS-level popups that stay visible when pywebview loses focus.

**`confirm()` returns a Promise.** In async DOM listeners, use `.then()` chains over `await` — pywebview's event dispatch doesn't wait for async handlers.

**`localStorage` and `sessionStorage` are not available as globals in pywebview's WebKit2GTK context.** Always use `safeLocal` / `safeSession` from `playdate.js` instead. These fall back to in-memory objects when the native APIs are unavailable.

**`input.js`** — zone-based state machine (`nav`, `content`, `modal`, `ctx-menu`). Modal buttons need `data-modal-row`. Gamepad: XB layout, 400ms initial / 150ms repeat, 0.35 dead zone. `input[type=range][data-modal-row]` is gamepad-navigable: left/right adjusts by the slider's `step` attribute. For checkboxes, use `div[data-modal-row]` with an onclick toggle (`var cb=this.querySelector('input');cb.checked=!cb.checked;`) and `onclick="event.stopPropagation()"` on the inner checkbox. **Never use the HTML `disabled` attribute on buttons that need gamepad navigation** — `disabled` excludes them from `_modalGrid()`; use CSS `opacity` + a JS guard in the handler instead.

**File dialogs in pywebview:** `input[type=file].click()` is silently blocked when called from a gamepad RAF handler (non-user-gesture context). Use `window.pywebview.api.pick_open_path(filters)` instead, with a fallback to `.click()` for browser mode. After any native file dialog closes, WebKit2GTK fires a spurious click on the focused element, which reopens the dialog. Guard every file dialog function with `_fileDlgBusy` (a shared flag, 300ms `setTimeout` to clear) to absorb it.

## HLTB Integration

Times are in minutes. `hltb_fetched`: `NULL`/`'0'` never fetched; `'unconfirmed'` matched below threshold (times NULL); `'no_match'` no results **or dismissed via the modal's "No page" button** (`DELETE /api/hltb/<appid>` -> `delete_hltb`); `YYYY-MM-DD` confirmed. Startup catch-up (`sync_hltb_unfetched`) fetches only `NULL`/`'0'`, never `no_match`, which is what makes "No page" stick. A `no_match` game stays in the modal's "no match found" section with a Search button, and `Re-scrape` (`POST /api/hltb/<appid>`) still re-fetches on demand.

**Every `howlongtobeatpy` call is wrapped in `_hltb_bounded()`** (`scrapers.py`): a hard `_HLTB_CALL_DEADLINE` (75s) via a daemon thread + `Event.wait()`, because `requests` only has a per-read timeout (60s, not a total) and a slow-trickle connection otherwise blocked forever, freezing bulk progress and defeating the abort-after-5-`HLTB_UNREACHABLE` guard (which only advances when a call returns). On deadline it raises `TimeoutError`; `fetch_hltb_data`/`fetch_hltb_by_id` map it to `HLTB_UNREACHABLE`, `search_hltb_results` to `[]`. `bulk_hltb_confirm_matches` logs `[bulk_hltb_confirm] i/N appid=... id=... name` per game.

**`howlongtobeatpy` breaks when HLTB changes its API** (it rotates an obfuscated search path + embedded key in its JS bundle; an unparseable pinned lib 404s every lookup). Keep it current (`1.0.21` -> `1.0.23` for v1.9.0). `fetch_hltb_data()`/`fetch_hltb_by_id()` return the `HLTB_UNREACHABLE` sentinel (`scrapers.py`) when no request reached HLTB, to tell "down" from "no data". **Callers must never clear a stored match on `HLTB_UNREACHABLE`**, only on a genuine reached-but-empty result. Confirm/select/rescrape routes return HTTP 502 `{'unreachable': True}` then; bulk workers count a transient failure and leave `hltb_fetched` untouched.

**"Confirm all above threshold" is a bulk op** (`op='hltb_confirm'`, `bulk_hltb_confirm_matches()` in `scrapers.py`), so it survives closing the modal, driven by `/api/bulk-op/start|status|cancel` and the top-bar progress button. `bulk_op_start` builds the appid list from the passed `threshold` (the live slider, which may differ from the saved `hltb_match_threshold`). The modal re-attaches its poller (`_hltbAttachBulkPoll`) if a `hltb`/`hltb_confirm` job is running. Aborts after 5 consecutive `HLTB_UNREACHABLE`.

## Update Rollback (`rollback.py`)

If an update fails to start, the previous version is restored automatically. The new version can't be trusted to do this itself (it may not even import), so **the old version sets everything up before handing over** and a detached watchdog started by it supervises the new version's first start. `rollback.py` is stdlib-only and imports nothing from the app, because the watchdog runs from the old version's own copy of it.

- **Flow:** `updater._rb_begin(kind, snapshot_fn)` backs up user data (`backup_data`: `games*.db` through sqlite's backup API, `config/state/theme.json`), takes the code snapshot, then writes `.rollback/pending.json` (`old_pid`, versions). Any failure there is logged and the update proceeds unprotected: a missing safety net must never block updating. The new version deletes `pending.json` in `app.py`'s `after_request` on the first 200 HTML response for `/`, `/library` or `/pick` (not `__ready__`, not the splash; proof the window got a page), ignoring the process that wrote it (`old_token`, a per-process random id; **never a pid**: every Flatpak sandbox has its own PID namespace, the old and new app both ran as pid 2 and the new one mistook itself for the old, found live on a Deck), and frees the snapshot.
- **Failure = exit code != 0 before healthy, twice** (`ATTEMPTS`). Exit 0, or still alive after `HANG_LIMIT` (180s) without healthy, is left alone: a slow migration must not trigger a rollback. On failure: restore code, restore data (deleting `*.db-wal/-shm` first, or the failed version's WAL gets replayed onto the restored DB), write `rolled_back.json`, start the old version.
- **After a rollback:** `housekeeping()` (at `create_app`) folds `rolled_back.json` into `failed.json`; `updater._is_failed_version()` stops `available` for that version (a newer one is offered normally); `base.html` shows a one-time notice via `/api/rollback-notice` (+ `/dismiss`). The user's `playdate.log` is deliberately not restored, so "Send Log" still has the failure.
- **Per install type:** *Source:* snapshot only the files the zip will overwrite (+ the list it creates, deleted on rollback); watchdog is `.rollback/watchdog.py` (copy of `rollback.py`) run with `sys.executable`; also restores at once if extraction throws. *Windows:* copy `PlayDate.exe` + `_internal` to `.rollback/code/` and run the watchdog from `PlayDate-Rollback.exe` there (`main.py` handles `--pd-watchdog` first). The installer, not the watchdog, starts the new exe, so the watchdog waits for the image to appear (`tasklist`) and can only see it vanish, not its exit code; that counts as attempt one, then it starts the exe itself for attempt two. Skipped if the layout isn't `PlayDate.exe` + `_internal` or the disk is too full. *Flatpak:* the installed commit is copied into a small local OSTree repo `.rollback/repo` (+ `repo.ref`) with `flatpak build-commit-from` (`updater._rb_flatpak_copy_installed`, ~3 s; PlayDate makes the empty repo itself, `rollback.make_empty_ostree_repo`, since the host may lack `ostree`); rollback adds it as a temporary `pd-rollback` remote and runs `flatpak install --user --reinstall --no-deps` (the runtime is already installed). `flatpak build-bundle` into `.rollback/old.flatpak` (~2 min, one core) is the fallback if the copy fails, run while the new bundle downloads; the watchdog restores whichever exists. A later reinstall from the usual remote and `flatpak repair` were verified after a rollback, **not** a later real bundle update. The watchdog is `FLATPAK_WATCHDOG_SH` run on the host via `host_popen` (POSIX sh; the host may lack python3), started through `sh -c 'setsid "$@" &'` (spawned directly, the `flatpak-spawn` client keeps the old sandbox alive). `--user` installs only. Steam Deck Game Mode launches through Steam, so the script runs in `observe` mode: it snapshots the `flatpak ps` instance ids before launching and judges only the instance its own launch creates (the old sandbox lingers and used to hide a crash). The script is written by the OLD version, so a fix only protects updates made from a build containing it.
- **Source installs stamp the build (v1.12.1):** the source updater extracts GitHub's tag zip, whose `config.py` still says `__build__ = __version__` (bare `X.Y.Z`), so a source user on a beta used to report the final number and was never offered the next beta. After extracting, `updater._stamp_source_build()` rewrites that line to the full release tag (checked against a strict version pattern first, since it lands in Python source; a failure only logs). Tested in `tests/test_update_versions.py`.
- **Protection starts with the update *after* the one that ships this**, since the old version does the setup.
- **Verified:** `tests/test_rollback.py` (snapshot/restore, health marker, the source watchdog end to end with a crashing stand-in app, the Flatpak shell script against a fake `flatpak`), the `after_request` hook, and `flatpak build-bundle` on a real bundle-installed app. **Not verified live:** the Windows path (`tasklist` detection, running the exe copy as the watchdog, restoring over a just-installed tree) and the Steam Deck `observe` mode; test both on real hardware before relying on them.

## Renaming PlayDate to Zest (planned, not done)

Decided 2026-10-06 and deliberately NOT shipped in 1.12.0: the app becomes **Zest** (the acronym is ZEST = Zest Enhances Spare Time). The full name "Zest Library Manager" is only for the GitHub repo/page; everywhere else, including the window title, installer and tutorial, it is plain "Zest". Every instance of the name is to be renamed eventually, but not all in one step, and some things must keep working for installs that already exist.

- **The Flatpak app IDs never change** (`io.github.robbyratpoison.PlayDate` and `.Qt`). They are invisible to users, and a new ID would be a different app (no in-place update, no data, a dead Steam shortcut) needing a migrator that would have to ship *before* the rename, because only old code can move an old install.
- **No migration engine is needed.** Windows and source installs get the rename as a normal update. Installed copies keep finding releases because GitHub redirects a renamed repo's API and download URLs (the updater picks assets by extension, `.exe` / `.flatpak` / `-qt.flatpak`, never by name). The redirect lasts only until someone creates a new repo with the old name, so the rename release also puts the new slug first in `updater.UPDATE_REPOS` (the old one stays as a fallback).
- **Versions are calendar versions (`YYYY.M.N`) from the release after 1.12.0 (decided 2026-10-07):** that release is `2026.10.1` and still PlayDate; the rename ships a month later as `2026.11.x`. N counts releases within the month and restarts at 1. A calendar version outranks every `1.x`, so installs still see it as an update; restarting at 1.0.0 would not. Every version parser already takes dotted numbers (`tests/test_update_versions.py`), and `release.py` suggests the next one (`_next_plugin_version`, shared with plugins). Shipping the numbering a release early means any problem with it shows up before the rename.
- **The update dialog already says the new name before the rename ships (v2026.10.1):** `config.RENAME_FROM_VERSION` (`2026.11.0`, injected as `window._RENAME_FROM`) is the first version that goes by the new name. `base.html`'s `_updateAppName()` / `_isRenameUpdate()` use it, so an install offered `2026.11.1` shows "Install Zest v2026.11.1?" plus a one-line "PlayDate is now Zest" notice, and the menu label names it too; before that version everything still says PlayDate. It is deliberately not in the release notes (the owner wants the rename to be a surprise). The rename update needs no separate warning release; the `notifications.json` banner covers launch. If the rename slips past November, move `RENAME_FROM_VERSION` before releasing any version at or above it.
- **Already prepared (1.12.0):** `rollback.py` no longer hardcodes `PlayDate.exe`. `snapshot_frozen` records the running exe's own name, the Windows watchdog watches for any of `rollback.ALT_EXE_NAMES` (`Zest.exe`) as well as the old name, and a rollback removes the renamed exe. The update that renames the exe is run by the OLD version's watchdog, so it had to know the new name in advance. `updater.UPDATE_REPOS` is the single list of repos the update check asks (first 200 wins).

## Update Confirmation Backup Cooldown

`update-confirm-overlay` (base.html)'s "Back Up First" button is hidden, and its hint text swapped, whenever `GET /api/backup-status` (`backup.py`) reports a backup completed within `BACKUP_COOLDOWN_SECONDS` (24h). `last_backup_at` (a `state.json` unix-timestamp float) is written by both `/api/backup` and `/api/backup-to-path` on success. Checked fresh via fetch every time `handleUpdateBtn()` opens the modal, not injected at page load - completing a backup doesn't reload the page, so a stale server-rendered flag would still nag immediately after backing up, which is the exact complaint this fixes.

## Log Submission

System modal → Support → "Send Log to Developer" (`send-log-modal` in `modal_tools.html`, `submitLog()` in `modal_tools.js`) posts `playdate.log` (last 4MB, matching the `RotatingFileHandler` cap) plus version/OS/install-channel and an optional user message to `POST /api/submit-log` (`diagnostics.py`), which forwards it to a Cloudflare Worker relay (`tools/log-relay/`), which in turn posts it to Discord as two attachments. `config.json` is never sent — it's the only file holding API keys/account tokens. `state.json` has no credentials in it, so `_diagnostics_snapshot()` sends its full contents (filters, hidden platforms, shelf layout, etc.) as a second attachment (`diagnostics.json`, capped at `MAX_DIAG_BYTES`), alongside library/platform game counts, installed plugin versions, and active renderer — useful for bugs the log text alone doesn't explain (e.g. an empty library page caused by `hidden_platforms`/a saved filter). The relay's Discord forward uses the indexed `files[n]` + `payload_json.attachments` multipart format to send both files in one message; an un-redeployed older relay just ignores the unrecognized `diagnostics` field and posts the log alone. Server-side cooldown (`SUBMIT_COOLDOWN_SECONDS`, 5 min, tracked via `state.json`'s `last_log_submit_at`) prevents spam-resubmission from the app itself.

`RELAY_URL` in `diagnostics.py` is a plain constant (not an env var) because it needs to be baked into the shipped binary for every user, not configured per-install. If it's ever blank, the route 501s instead of erroring. Because it ships inside public source/binaries, it's discoverable and postable-to by anyone — but unlike the raw Discord webhook URL this constant used to hold directly (found and abused via public git history, see `tools/log-relay/README.md`), the relay only ever forwards a fixed message template and never lets a direct caller inject raw content/mentions/embeds, so finding this URL doesn't hand out a "post anything to our Discord" credential the way the old constant did. The real Discord webhook now lives only as a secret on the relay (never in source), with its own KV-backed per-IP rate limiting as a second backstop.

## SteamGifts Wins Import (`steamgifts.py`, added v1.9.2)

Gathers SteamGifts (SG) "won" data without BLAEO. Cloudflare blocks the backend from scraping SG, so `steam_date_import.user.js` (SG `@match` for `/giveaways/won*` and `/user/*/giveaways/won*`) fetches pages in the user's own logged-in browser and POSTs raw HTML to `steamgifts.py`; PlayDate opens the tab and the script reports back. Two passes: **public** `/user/<name>/giveaways/won` (every field, but invite-only/group giveaways lose their code for a non-winner) and **private** `/giveaways/won` (opt-in, authoritative received-state for wins the public page left "Awaiting feedback"). The private page embeds live Steam keys; parsing never selects the key node and `_scrub()` drops any value that still looks like one (a hard trust boundary).

**Storage:** gitignored per-account `steamgifts_wins_<steamid>.json` next to `games.db`, keyed by appid, list-valued; no DB columns for win date/points/gifter. The *only* DB write is the `"Won on SteamGifts"` group, and only for a game with a win confirmed `received: true`.

**Sync is incremental by default** (newest-first, stops at the first unchanged recorded page); `merge_public_page()` only adds/updates a win by its dedup key (giveaway code, or `(steam_ref, won_ts)` when the code was stripped). **"Full Refresh" is the only way anything is removed**: `apply_wins(full_refresh=True)` prunes group membership for games that no longer qualify **and** (v1.10.5, GitHub issue #3) drops any win record the scan didn't re-confirm (e.g. scraped under a mistyped username). That works because a full refresh is exhaustive (early-stop disabled), so `merge_public_page(..., full_refresh=True)` tags re-confirmed records (`_seen_this_run`) and `apply_wins()` drops the untagged. An incremental sync can't tell "gone" from "not re-scanned", so it never prunes.

**Unmatched wins** (no library row) get a one-line reason from `_classify_unmatched()` via Steam's `appdetails` (cached, 1s-throttled). Two follow-ups, both through `_adopt_into_group()`:
- **Delisted game the user still owns** -> `POST /api/steamgifts/wins/adopt` recreates the row from local Steam files (`appinfo.vdf`, `localconfig.vdf`, ACF) since `GetOwnedGames` omits it.
- **DLC/soundtrack for a game already in the library** (v1.10.5) -> the win is *never* its own row; `_classify_unmatched()` also returns the base appid from Steam's `fullgame` field and `POST /api/steamgifts/wins/adopt-dlc-base` tags the owned base game. `sg_unmatched()` checks ownership fresh at read time. A `sub/` package win gets the same treatment (a season-pass package can bundle only DLC appids, so the branch scans each bundled app's `fullgame`). The DLC win record is flagged `dlc_base_adopted` (checked by `apply_wins()`'s unmatched loop) so it stops reappearing; **don't** repoint its `appid` at the base game, which would fold it into `received_by_appid` and let a full refresh un-adopt the base. `_appdetails_lite()`'s persisted cache has no schema versioning, so a per-key check like `'fullgame_appid' in cache[key]` is required whenever its return shape gains a field, or old entries keep the old shape forever.

**`sg_username` is per-account** (`config.get_sg_username()`, active account's value else a legacy top-level fallback; PAGYWOSG per-user verification keys off it), normalized idempotently on every config load, since an old backup with the legacy key can be restored at any time.

## PAGYWOSG Filter Builder

PAGYWOSG ("Play A Game You Won On SteamGifts") is an independent community event (`pagywosg.xyz`), not part of SteamGifts; it just requires the submitted game to have been won there. Each month sets its own qualifying categories; users pick a game, a category and any notes it requires, and submit manually on the PAGYWOSG site. PlayDate never submits anything; it builds the filter and shows what qualifies. Submitters also mention their pick in the event's SG discussion thread (the site can't contact them). PAGYWOSG mods are regular SG users, not SG staff.

The tool (`modal_tools.html`) builds structured filter trees for the monthly event; categories are fetched live from `pagywosg.xyz` (no static catalog).

**`pagywosg.py`** is the single source of truth for classification and the operator vocabulary. `classify_category(base, base_appids, icaio_ga, icaio_wl, santa)` pattern-matches a category name into a neutral op (`OP_REGISTRY` key: `month_is`, `contains`, `title_word`, `digit_count_gte`, `has_special_char`, `range_incl`, `nth_weekday`, `contains_all`, etc.) or falls through to the mod-verified appid list (`reason: 'verified_fallback'`/`'unhandled'` = *not* automated; see the scanner). Each `OP_REGISTRY` entry carries the SQL "kind" (dispatches `redundant_where_sql()` and the JS `pagCondToTree`/`pagCondToSql`/`_pagCheckCond` in modal_tools.html/modal_edit.html), the saved-tree `tree_op` token and the condition-builder label. `window._PAG_OPS` injects the registry into every page. A category reusing an existing op is one new regex branch in `classify_category()`; a new op needs an `OP_REGISTRY` entry plus all three SQL/JS consumers.

**Event ID formula:** `pagywosg.pagywosg_event_id(year, month)`: one event per month, event 1 = June 2019 (`PAGYWOSG_EPOCH_*`), id = month offset from that anchor (verified against the live API, events 1-87, no skipped months). Reused by `pagywosg_auto()`, `pagywosg_quals_data()` and the scanner's `_current_event_id()`.

**Pool rules:** categories with both `(win)` and `(backlog)` variants -> "all" pool; no suffix -> "wins" pool.

**Filter tree:** root AND with `platform = 'steam'` first, then OR of [all-pool branch, AND[steamgifts-won condition, wins-pool branch]], plus completion-status exclusions and `appid IN (...)` for mod-verified games.

**icaio detection:** exact phrases: `"icaio has made a GA for"` -> giveaways list; `"icaio"` + `"wishlist"` -> wishlist (exact to avoid false positives). These get `auto: true` (suppresses "mod verified"). **Supplement file** `pagywosg_supplement.json`: `icaio_giveaways` (list of `{appid, name}`) and `icaio_wishlist` (`{appid_str: name}`).

**Personal categories & per-user verification:** each verified entry carries the verifier's `sgProfileName` (`pagywosg.build_verified_by_cat()`). A category marked "personal" only includes appids verified for the current `sg_username`: `/api/pagywosg-auto`'s `appid_sources` carries `appids` and a `personal_appids` subset per label (server-side regardless of the client's toggles). `pagywosg_personal_defaults.json` (repo-tracked, ships with releases) holds `{event_id: [base_category_name, ...]}`, maintainer-curated categories that default to personal; `pagAutoFill()` pre-checks them (still toggle-able). `/api/pagywosg-quals` (live preview) has no toggle state, so it applies that default list directly.

**Saved filter keys:** `pagywosg: true`, `pagywosg_event: {id, name}`, `pagywosg_verified: {appid: [{cat, pool, verifiers?, auto?}]}` (`verifiers` = SG usernames). They must survive re-applying: `modal_filters.html` copies them from `_loadedSavedTree`, and `openFilterModal()` seeds `_loadedSavedTree` from the server tree when `pagywosg: true` and it isn't set.

**SG wins group:** `_pagSgGroup` in `modal_tools.html`: string = chosen group, `null` = no SG wins, `undefined` = not loaded; stored as `pagywosg_sg_group` in `state.json`; if unset with no default, a warning prompts configuration. **Quals panel:** `modal_edit.html` when `_serverFilterTree.pagywosg`; wins branch = a `groups` condition in any AND group. **Hover tooltip:** IIFE in `library.html`, only when `_serverFilterTree?.pagywosg`, event delegation on `#game-grid`.

**Category gap scanner** (`tools/pagywosg_category_scan.py`, dev-only): `python tools/pagywosg_category_scan.py [--event N | --events A-B | --next] [--all] [--triage]` buckets each category as automated vs not (fell through to the verified fallback). `--triage` walks the not-automated ones: `[n]` non-automatable (local `pagywosg_scan_decisions.json`, gitignored), `[p]` always-personal (writes the repo-tracked `pagywosg_personal_defaults.json`; commit to ship), `[s]` skip.

## Release Workflow

At release, distill completed work into user-facing notes for `RELEASE_NOTES.md`.

**CI build:** pushing a `vX.Y.Z` / `vX.Y.Z-beta.N` tag triggers `.github/workflows/build-windows.yml` ("Build Releases") — a Linux Flatpak job (creates the GitHub Release, attaches the `.flatpak`) then a Windows job (attaches exe + portable zip). The Flatpak job compiles tcl/tk/tkinter from source (~5 min) unless it gets a `.flatpak-builder` cache hit — and it can't, because Actions cache is ref-scoped and tag runs only see their own ref + `main`. `.github/workflows/flatpak-cache.yml` fixes that: it runs the same cache/build steps on `main` pushes (manifest/requirements changes), twice weekly, and on demand, so those caches exist on the `main` scope for tag builds to restore. The manifest-patch step and cache keys must stay identical between the two workflow files.

`release.py` (gitignored, local-only) also checks the official plugins' local `plugin.json` versions against their published GitHub releases (`check_official_plugin_updates()`) as part of both `main()` and `main_beta()`, and offers to push+tag+release any that are ahead (`publish_plugin_update()`). Non-blocking — a plugin repo being behind doesn't stop a PlayDate release — and only finds anything to do if the maintainer has one checked out locally with unpublished changes, since fixing a bundled-turned-catalog plugin no longer ships automatically with the next PlayDate release the way it did when the source lived in this repo. (`release.py` keeps its own list of which plugin repos to check — update it there when the `OFFICIAL_PLUGINS` set changes.)

**Plugin versions are calendar versions too (`YYYY.M.N`, from 2026-10-07, Epic Games first; PlayDate itself follows from `2026.10.1`).** N counts that plugin's releases within the month and restarts at 1 each month; `release.py`'s `_next_plugin_version()` computes it, and a plugin still on `1.x` moves to the current month's `.1` at its next release (2026.x outranks any 1.x, so updates are still offered; `plugins._semver` compares plain numbers). Plugins have no release notes of their own, so the GitHub release note for a plugin comes from its `plugin.json`: `"release_note": {"version": "<the version it is for>", "text": "<one line>"}`. `release.py` uses it only when `version` matches the version being published, else the generic "Synced with the version bundled..." line. Write the note when you change the plugin; user-facing wording still goes in PlayDate's own `RELEASE_NOTES.md` at the next core release.
